# 单词趣味配对 · 微信小程序源码

这个压缩包由 Story-Creator 的「单词匹配」页导出（`/learn/word-match` → 设置 → 导出小程序源码）。
包里的词库是导出那一刻按后端切关算法现算的，与网页版完全一致。

## 里面有什么

```
app.js / app.json / app.wxss     小程序入口与全局样式
pages/index/                     检索首页（按册次、按单词查）
pages/play/                      配对玩法页（主包版：只配对，不出声）
utils/                           词库访问、检索、音效、读音、进度存储
data/books.js                    全部册次的元信息（id / 名称 / 学段 / 关数 / 词数 / 有无读音）
data/levels-<学段>.js            各学段全部关卡（每关：主题 + 单词对）
packages/<册>/                   读音分包（只有已经生成读音的册才有，见下）
```

`data/` 与 `packages/` 都是**生成物**，每次导出都是当前状态的最新快照；不要手改，
改词库请改 Story-Creator 里的词库源（`src/main/resources/learn/*.json` 与对应的切关逻辑）。

## 关于读音分包（重要）

已经生成读音的册（目前是小学 3~6 年级，共 8 册）各自有一个分包：

```
packages/<册>/play/              该册的玩法页（与 pages/play/ 同一份代码）
packages/<册>/audio/sprite.m4a   整册读音（一册一条，约 0.5~1.4 MB）
packages/<册>/audio/index.js     读音索引：[[词, 起点秒, 终点秒], ...]
```

为什么不是一个音频文件一个词、或者干脆放主包：

- **整册一条 sprite**：一册只下载 1 次，点第二个词是零延迟；逐词一个文件会让一册产生上百次请求。
- **必须分包**：主包上限 2048 KB，8 册音频合计约 7.3 MB，塞不进去。
- **播放页必须和音频同处一个分包**：微信规定「主包不能使用分包资源」——
  在开发者工具里能播，真机上静默无声（官方社区已明确答复）。

所以主包的 `pages/play/play` 只做一件事：发现当前册有读音，就 `redirectTo` 到
`packages/<册>/play/play`；没有读音的册原地跑，行为与之前完全一致。
进入某册时首次要等分包下载（几百 KB 到 1.4 MB），之后就缓存在本地。

## 怎么跑起来

1. 解压，得到 `word-pair/` 目录。
2. 打开微信开发者工具 → 导入项目 → 选择这个目录。
3. `project.config.json` 里的 `appid` 是空的：
   - 有自己的小程序，填自己的 AppID；
   - 只想本地看效果，导入时选「测试号」即可。
4. 无需后端：进度、错题本全部存在本机（`wx.setStorageSync`），不依赖任何服务器。

## 发布前

- 小程序名称与类目需要和实际内容一致（本项目用的是「工具 - 信息查询」类目）。
- 体积：主包约 0.9 MB（上限 2048 KB），最大的读音分包约 1.5 MB（单分包上限 2048 KB），
  总包约 8.9 MB（上限 20 MB）。**再加册次时要重新核对**：单册音频超过 1.9 MB 就得拆。
- 上传、提交审核、发布都在微信公众平台/开发者工具里完成。
- 分包目录是导出时生成的，新增册次的读音只需重新导出，不用手改 `app.json`。

## 想改玩法

改 Story-Creator 仓库里的 `src/main/resources/miniprogram-template/`，然后重新导出。
这份源码是模板 + 数据的产物，直接在本包里改会在下次导出时被覆盖。
